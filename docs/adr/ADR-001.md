# ADR-001: Remove the Student Class from the Domain Model

**Status:** Accepted  
**Project:** Student Task Tracker  
**Course:** EECE 4081 — Software Engineering

## 1. Context

My Student Task Tracker is a web application that helps students organize their academic work. Students can create tasks, set due dates and priorities, mark tasks as completed, and view pending and completed tasks.

During IAP M3, I used GitHub Copilot to generate an initial domain model. The AI suggested a Student class connected to the Task class through a one-to-many relationship.

I had to decide whether to keep the Student class or remove it from my final model.

My current requirements focus on managing academic tasks. They do not require student registration, login, or multiple student accounts.

Keeping the Student class would make the model more complicated and require additional work that is not necessary for the current version.

## 2. Decision

I decided to remove the Student class from my domain model.

The Task class will be the main class in the application. It will contain the task ID, title, type, due date, priority, and completion status.

TaskType and Priority will remain as enumerations.

The application will manage tasks without a separate Student entity or Student-to-Task relationship.

## 3. Alternatives Considered

### Alternative 1: Keep the Student Class

I considered keeping the Student class suggested by GitHub Copilot.

This would allow tasks to be connected to individual students and make it easier to introduce multiple student accounts later.

However, I did not choose this option because my current requirements do not include student accounts or authentication. It would add unnecessary complexity to the domain model.

### Alternative 2: Use a Student ID in the Task Class

Another option was to remove the Student class but keep a studentId field inside Task.

This could help identify which student owns a task without creating a separate Student class.

However, I did not choose this option because the application currently has no system for creating or identifying different students. The studentId field would not serve a useful purpose at this stage.

## 4. Consequences

### Positive Consequences

- The domain model becomes simpler and easier to understand.
- I can focus on implementing the task management features required for the project.
- I do not need to create a separate Student model or manage relationships between students and tasks.
- The design stays close to my IAP M2 requirements.

### Negative Consequences

- The application will not support separate student accounts through the current domain model.
- If I decide to support multiple students later, I will need to introduce a Student or User entity and connect tasks to their owners.
- Adding accounts later may require changes to the database, existing task records, and application logic.
- Without a student ownership relationship, the current model cannot separate tasks belonging to different students.

## 5. Final Decision

I chose to remove the Student class because it is not necessary for the current version of my application.

Although keeping it could make future expansion easier, I believe starting with a simpler model is the better choice for now.

If the project later requires multiple student accounts, I will review this decision and update the domain model.
